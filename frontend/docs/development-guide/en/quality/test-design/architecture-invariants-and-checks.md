# Architecture invariants and checks

**Support status: installed frontend source guards and backend bytecode rules.** This is the navigation map for every currently installed mechanical architecture guard: its executable owner, fixture owner and command. It does not turn every development-guide recipe or semantic rule into an automated invariant.

Use it after a placement, import, feature Interface or backend dependency change. Read the owning architecture contract as well as the mapped check; a green result establishes only the scope described below.

## Frontend guard map

[verify-application-architecture.mjs](../../../../../../frontend/scripts/verify-application-architecture.mjs) collects `.ts`/`.tsx` files under `src`, `tests` and `mocks`, plus `vite.config.ts`. It calls [verifyApplicationArchitecture](../../../../../../frontend/scripts/application-architecture-policy.mjs), which runs `assertPositiveFixtures`, `assertNegativeFixtures`, `assertNoViolations` on current files, then `assertAuthenticationContract`.

All helper and fixture symbols in this table belong to that policy file. “Positive” and “negative” refer to the embedded functions above, built on `requiredFixtures`; they are not a separate test runner. A listed fixture illustrates the guard family, not exhaustive mutation coverage for every branch. Current-source-only guards are explicit.

Import extraction uses TypeScript ASTs for static imports/exports and literal dynamic imports. `moduleCandidates`/`resolvedModulePath` resolve configured alias/relative filesystem candidates, including `.js` references to TypeScript sources. Some guards inspect text rather than bound symbols. Arbitrary computed imports, runtime reflection, alternate loader resolution, indirect data flow and business meaning are not proved by these checks. Source-pattern checks can also reject equivalent spelling changes until their owner updates the contract and proof together.

## Backend guard map

Current working-tree owners are [ArchitectureTests](../../../../../../backend/src/test/java/com/vireocode/backend/architecture/ArchitectureTests.java), [BackendArchitectureRules](../../../../../../backend/src/test/java/com/vireocode/backend/architecture/BackendArchitectureRules.java) and [ArchitectureRuleProofTests](../../../../../../backend/src/test/java/com/vireocode/backend/architecture/ArchitectureRuleProofTests.java). The [backend package/Interface contract](../../backend/foundation/http-service-persistence-boundaries.md) defines the actual published types and operations.

The production suite has six ordinary JUnit checks after the complete-main import precondition. Proof methods import explicit positive/violation graphs under `backend/src/test/java/architecturefixtures/`; those fixtures never join the production import.

| ------------------------------- | ------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

`featureCycles(applicationPackage)` uses `slices().matching(applicationPackage + ".(*)..")` with `beFreeOfCycles()` and `allowEmptyShould(false)`. It sees static dependencies, including generic signatures, between first-level feature slices. Bootstrap and external packages do not match slices. Empty or wholly nonmatching input fails because no slices are checked; mixed input is not rejected merely for containing an outside class. The separate complete-main import and `featureBoundaries` guard production scope/bootstrap placement. Intra-feature class cycles, Spring bean cycles and reflection are different questions.

## Commands and CI owners

Use the repository's required Node/npm and Java toolchains. These are the existing commands, not a new scheduler:

```sh
npm --prefix frontend run verify:architecture
cd backend
./gradlew --no-daemon --console=plain test --tests '*.architecture.*'
```

The frontend command runs embedded positive/negative fixtures before current-source checks. Backend `test` also includes both architecture suites; `./gradlew --no-daemon --console=plain test bootJar` remains the complete backend verification command.

[ci.yml](../../../../../../.github/workflows/ci.yml) runs frontend architecture in the selected `frontend` static lane. Backend `backend-tests` shards use [test_shards.py](../../../../../../infrastructure/ci/test_shards.py) to discover normal JUnit methods through `ciTestInventory` and execute every assigned class. Main bytecode import occurs in `BeforeAll`, so dry-run inventory does not execute it. Existing console/JUnit/shard results are the evidence; this article adds no unified invariant-report format or bypass protection.

Run focused checks during implementation, then the required final gates sequentially under the root agent's resource coordination. An intentional fixture must be rejected for the expected rule; a build failure or unrelated assertion does not prove that invariant.

## Review obligations and change procedure

Review still decides whether an Interface is appropriate, a capability name or factory is useful, an exception is justified, and the documentation matches current behavior. Backend DTO/mapper purpose, authorization, persistence/concurrency correctness, direct JDBC/EntityManager access, aliasing and runtime bean/reflection collaborations remain semantic obligations. Frontend runtime/profile behavior and every uninstalled reference recipe likewise need their own evidence.

For an approved invariant change, update its source contract, executable guard and accepted/violation fixtures together, then revise this map in both languages. If a guard has no dedicated negative fixture, say so rather than manufacturing passed evidence. Missing patterns or a proposed weakening follow the root approval gate; editing a check or fixture cannot approve the agent's own departure.
