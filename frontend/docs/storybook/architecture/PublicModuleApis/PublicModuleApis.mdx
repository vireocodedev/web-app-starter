# Public module APIs

A feature's `index.ts` is its deliberate public interface. Export the members actual consumers need and retain private implementation behind that seam.

## Before you start

Paths are relative to `frontend/`. Read `docs/architecture/en/feature-anatomy-filenames-and-public-interfaces.md`, `docs/architecture/en/dependency-boundaries-and-imports.md`. Inspect the current implementation and its callers before reusing a pattern. Contacts lives only under `docs/storybook/examples/Contacts/`; installed Settings and app infrastructure remain under `src/`. Consumer recipes describe explicit installation work, not APIs already registered in the app.

The Contacts reference at `docs/storybook/examples/Contacts/index.ts` deliberately exports feature-level UI and its factory/hook. Those are **documentation APIs**, not members of the production runtime. A consumer implementing equivalent behavior chooses its own `src/features/<feature>/index.ts`.

```ts
// Excerpt: reference Contacts public exports, relative to its owner.
export { ContactsFeature } from "./components/ContactsFeature";
export { ContactsDashboard } from "./components/ContactsDashboard";
export { createContactsFeature, type ContactsFeature as ContactsFeatureRuntime } from "./contacts.feature";
export { useContactsFeature } from "./hooks/useContactsFeature";
```

Export only warranted members. A presentation feature needs no factory or runtime hook for symmetry.

## 2. Cross a feature through its public index

```tsx
// Excerpt: consumer page, after implementing this feature in src.
import { ContactsFeature } from "@/features/contacts";
```

Pages and approved runtime composition use deliberate named exports. They do not reach into `components/ContactForm`, a model or a private Context. Within the owner, relative imports are normal. Avoid `export *` barrels and indirect Context/internal leaks.

## 3. Distinguish a module API from an internal port

`docs/storybook/examples/Contacts/api/contact.api.ts` defines the reference persistence port. It is used internally by adapters and data factories; it is not the public module surface. An exported symbol in an internal file is not automatically a cross-owner API. Decide whether a new consumer needs public UI, a narrow operation or different composition before exporting internals.

## 4. Respect application leaves and runtime wrappers

A feature may consume approved app interfaces such as:

```tsx
// Approved application leaves; the feature supplies its own labels and rules.
import { AppSingleChoiceToggleGroup } from "@/app/forms/components/AppSingleChoiceToggleGroup";
import { useAppTranslation } from "@/app/localization/hooks/useAppTranslation";
```

The reference `useContactsFeature` reads a private preview Context. It is not a production `useAppFeature("contacts")` registration. An installed runtime feature instead adds its factory/type to `appFeatures.ts`, creates one canonical owned lookup wrapper and publishes that wrapper deliberately. See Building a backend-connected feature for the complete production recipe.

## Common mistakes

- Confusing internal exports with a public module interface.
- Publishing a private Context through another barrel.
- Repeating generic runtime keys outside the canonical feature wrapper.
- Copying a docs provider into production without deliberate runtime ownership.

## 5. Verify your implementation

Run from the workspace root:

```sh
npm --prefix frontend run verify:architecture
npm --prefix frontend run verify:dev-guide
npm --prefix frontend run typecheck
```

Run the owning focused tests and required final checks. Static verification checks placement, imports and declared contracts; it cannot establish product ownership, backend authority or runtime cleanup by itself.
