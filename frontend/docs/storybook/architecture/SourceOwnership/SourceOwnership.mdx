## 1. Choose the owner

Read `docs/architecture/en/source-map-and-ownership.md` and `feature-anatomy-filenames-and-public-interfaces.md` first. Paths here are relative to `frontend/`.

```text
src/app/             stable infrastructure and application composition
src/features/        installed product behavior (currently Settings)
src/pages/           thin route entries
src/main.tsx         startup

docs/storybook/examples/Contacts/  complete reference feature, outside the app
docs/storybook/patterns/           focused interactive reference panels
```

Application form mechanics live in `src/app/forms/`; feature values, validation and commands belong to their own feature. Settings presents preferences owned by app theme/localization/shell services. Do not create global `src/shared`, `src/common` or `src/utils` to postpone the ownership decision.

## 2. Add only required responsibilities

Contacts illustrates a feature with a persistence port, schema, data options and UI:

```text
docs/storybook/examples/Contacts/
├── index.ts
├── contacts.feature.ts
├── api/
├── components/
├── hooks/
└── models/
```

Its reference factory now receives both `api` and `queryClient`; its preview selects private memory data. The browser-storage adapter remains an inert, tested reference. Settings needs neither a factory nor an API folder. Avoid empty directories and factories added for symmetry.

Use `PascalCase.tsx` components, `useName.ts` hooks, `<domain>.api.ts` ports, `.api.<adapter>.ts` adapters, `.query.ts`, `.mutation.ts` and `.querykeys.ts` data roles. A factory exists only when construction owns dependencies.

## 3. Keep a consumer page thin

This is a consumer recipe, after implementing a public feature at `src/features/contacts/`; that owner is not installed by these docs:

```tsx
// Recipe: src/pages/contacts/ContactsPage.tsx
import { ContactsFeature } from "@/features/contacts";

export function ContactsPage() {
  return <ContactsFeature />;
}
```

The page composes the public interface. The feature owns queries, validation and editing. The router owns URL, access, title and navigation. Installing the reference requires explicitly choosing a real adapter, runtime registration and canonical hook; see Building a backend-connected feature for a complete installation recipe.

## 4. Mirror verification owners

```text
src/features/<feature>/       tests/features/<feature>/
src/app/<capability>/         tests/app/<capability>/
docs/storybook/examples/Contacts/  tests/storybook/contacts/
docs/storybook/patterns/      tests/storybook/patterns/
tests/integration/           cross-owner scenarios
tests/browser/               assembled flows
mocks/                       development HTTP boundary fixtures
```

Use `@/` for installed source and relative imports for documentation reference tests. Production must never import docs, tests or mocks. Keep tutorial MDX, CSF and fixtures in the same-name folder; section helpers live in `shared/`.

## Common mistakes

- Putting domain validation in the router or stable application shell.
- Treating the reference Contacts tree as an installed product feature.
- Creating a feature factory for presentation alone.
- Moving a feature without tracing tests, registrations, routes and persistence.

## 5. Verify your implementation

Run from the workspace root:

```sh
npm --prefix frontend run verify:architecture
npm --prefix frontend run verify:dev-guide
npm --prefix frontend run typecheck
```

Run the owning focused tests and required final checks. Static verification checks placement, imports and declared contracts; it cannot establish product ownership, backend authority or runtime cleanup by itself.
