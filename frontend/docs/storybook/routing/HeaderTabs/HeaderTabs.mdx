# Pages with header tabs

Build one Workspace destination with Overview and Activity pages sharing the
application header. Each tab has a URL, and Activity stays selected on its details
page. Use this pattern when users should be able to link to, reload, and navigate
back to an individual section.

```text
/workspace                    → /workspace/overview
├── /workspace/overview       Overview tab
└── /workspace/activity       Activity tab
    └── /workspace/activity/details
```

The router owns the hierarchy and navigation metadata. The existing shell builds
the header tabs from that metadata. The layout renders the selected child through
`Outlet`; each child remains an ordinary page.

## Try it

Choose Activity in the header, then open its details. The page changes while
Activity stays selected. The preview address bar displays the example's URL. Open
the canvas in a new tab for the full shell, or select **Mobile section menu** to
try phone navigation. Use the global Theme toolbar to check all four app themes.
Open the main menu and choose **Workspace** to return to its default Overview
page. Workspace remains selected in that menu on Activity and its details.

## Before you start

This recipe extends this starter's existing authenticated router, application
providers, and shell. It adds no backend endpoint. Use an initialized checkout
with dependencies installed and follow `frontend/README.md` for local startup.
Sign in before testing these URLs in the assembled application.

All paths in the implementation steps below are relative to `frontend/`. The
example pages contain only static presentation and links. When adding business

  overviewDescription: "A summary of the workspace.",
  activity: "Activity",
  activityDescription: "Recent changes in this workspace.",
  details: "Activity details",

Add the same keys inside `croatianTranslations` in

## 3. Register the parent, tabs, and details

In `src/app/router/routeRegistry.tsx`, add these page and icon imports. Reuse its existing `AppRouteDefinition` type import. Add `Outlet` explicitly;
the clean starter registry does not import it yet.

```tsx
import { Outlet } from "react-router";
import DashboardOutlinedIcon from "@mui/icons-material/DashboardOutlined";
import TimelineOutlinedIcon from "@mui/icons-material/TimelineOutlined";

import { WorkspaceLayout } from "@/pages/workspace/WorkspaceLayout";
import { WorkspaceOverviewPage } from "@/pages/workspace/WorkspaceOverviewPage";
import { WorkspaceActivityPage } from "@/pages/workspace/WorkspaceActivityPage";
import { WorkspaceActivityDetailsPage } from "@/pages/workspace/WorkspaceActivityDetailsPage";
```

Insert the five records below into the existing `appRouteRegistry` object,
alongside Home and Settings. Preserve its existing records,
`export const appRouteRegistry` declaration and route/navigation helpers. These are the complete Workspace records; they
use the application translation keys added in step 1.

```tsx
workspace: {
  Component: WorkspaceLayout,
  access: "authenticated",
  defaultChildId: "workspaceOverview",
  headerNavigation: true,
  navigation: { Icon: DashboardOutlinedIcon, labelKey: "workspace.title" },
  path: "/workspace",
  title: t => t("workspace.title"),
},
workspaceOverview: {
  Component: WorkspaceOverviewPage,
  access: "authenticated",
  navigation: { Icon: DashboardOutlinedIcon, labelKey: "workspace.overview" },
  parentId: "workspace",
  path: "/workspace/overview",
  title: t => t("workspace.overview"),
},
workspaceActivity: {
  Component: Outlet,
  access: "authenticated",
  navigation: { Icon: TimelineOutlinedIcon, labelKey: "workspace.activity" },
  parentId: "workspace",
  path: "/workspace/activity",
  title: t => t("workspace.activity"),
},
workspaceActivityIndex: {
  Component: WorkspaceActivityPage,
  access: "authenticated",
  index: true,
  parentId: "workspaceActivity",
  title: t => t("workspace.activity"),
},
workspaceActivityDetails: {
  Component: WorkspaceActivityDetailsPage,
  access: "authenticated",
  parentId: "workspaceActivity",
  path: "/workspace/activity/details",
  title: t => t("workspace.details"),
},
```

The existing `appRouteRegistry` already checks its records with
`as const satisfies Record<string, AppRouteDefinition>`. Omit
`translationNamespace` here: its default is the application `translation`
namespace. Keep the existing router and `AppShell` composition; registration is
sufficient to connect these pages to the header.

Only Overview and Activity are immediate children with navigation metadata.
Details remains under Activity, so it keeps that tab active. A nested group with

already covers this example; `navigation.activePath` is needed only for a
different match, with `/*` when that pattern includes descendants.

## 4. Add the drawer destination when needed

The parent navigation metadata provides its label and icon. Drawer membership is
explicit. In the same file, extend the existing list if Workspace belongs in the
main drawer:

```tsx
export const appNavigationItems = [
  homeNavigationItem,
  navigationLink(appRouteRegistry.workspace),
] satisfies readonly AppNavigationItem[];
```

Keep any other destinations already in that list. This uses the file's existing
`navigationLink` helper and `AppNavigationItem` import. It does not add a mobile
bottom-navigation shortcut; that list is a separate product choice. Without the
drawer entry, the registered Workspace URLs still work when opened directly or
through a normal router link.

The preview supplies Workspace to `AppShell.navigationItems`, so you can try the
main-menu entry as well as the header tabs. Its parent destination uses the same
default-child redirect shown in the recipe.

## Common mistakes

- **URL changes, child stays blank:** render `Outlet` in the parent layout and
  in any intermediate route, such as `workspaceActivity`, that owns children.
- **No header tabs:** set `headerNavigation` on the parent and `navigation` on
  its immediate children. A deeper child does not become a top-level tab.
- **Route validation fails:** each `parentId` must name a registered route, child
  access must equal parent access, and complete child paths must be beneath
  their parent. Use `/workspace/activity`, rather than `activity`, in this registry.
- **Conflicting default page:** use either `defaultChildId` or an index child
  for a particular parent. This example uses a redirect for Workspace and an
  index child for Activity; the two choices belong to different parents.
- **Keys appear instead of labels:** add the keys to both application locale
  resources and use `useAppTranslation`. Keep production text in the normal
  namespace; the fixture's `storybook.*` keys are registered only by Storybook.
- **Workspace is reachable but missing from the drawer:** add its explicit
  `appNavigationItems` entry from step 4.

## 5. Verify your implementation

From the workspace root, run the checks sequentially:

```sh
npm --prefix frontend run typecheck
npm --prefix frontend run verify:architecture
```

Expect both to exit successfully. Typechecking catches missing components and
translation keys or shapes. The architecture check covers import and ownership
rules. These checks do not prove browser navigation.

Start the application using `frontend/README.md`, sign in, and check:

- Open `/workspace`: the URL becomes `/workspace/overview` and Overview is active.
- Open `/workspace/activity` directly: Activity renders with Activity active.
- Open its details: the URL becomes `/workspace/activity/details`, details render,
  and Activity still has `aria-current="page"`.
- Use Back and Forward: the URL, content, and selected tab stay aligned. Reload a
  child URL and confirm it opens the same page after normal authentication.
- On a narrow screen, use More sections to change page. Reopen it and press
  Escape; it closes and restores focus to its trigger.
- Use the keyboard, switch the application's language, and check each theme.
  The route and active tab should survive presentation changes.

Use the existing route and shell tests as examples when adding automated
coverage: `frontend/tests/app/router/routeHierarchy.test.tsx` and
`frontend/tests/app/shell/components/AppShell.test.tsx`. Complete repository verification
with `npm --prefix frontend run verify` before delivery. A successful Storybook
build alone does not establish application deep-link or authentication behavior.
