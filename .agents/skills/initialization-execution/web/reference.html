Consumer initialization contract

Procedure

Consumer initialization contract

The execution skill owns running setup. The sibling intake skill owns the complete upfront questionnaire, saved answers and completed handoff. The runbook owns exact application edits and links to operator procedures.

Supported scope and target

Initialize one existing private GitHub consumer with one Git worktree containing frontend/ and backend/. Preserve the template stack, session authentication, examples, shared Hetzner CI and paired staging/production release workflows. Reuse the approved operator, shared App/pool, deployment host and supported backup destination. Creating a new foundation, changing privileged shared code, rebuilding a host, replacing data and implementing business features are separate tasks. Canonical vireocodedev/web-app-starter cannot initialize itself.

Intake handoff and authority

Execution's first operation is the intake require-complete gate. Missing, partial, invalid, changed or repository-mismatched intake stops execution with an explicit instruction to finish $initialization-intake first. A legacy workbook or old execution state is not a completed new intake.

Read the state contract. The helper derives readiness from valid applicable answers and prerequisites, and binds confirmation to their exact content and repository. A mutable complete: true flag alone is insufficient. Record the returned intake revision and digest in execution state; recheck them on resume and before phase writes. Answer changes require refreshed intake confirmation, while preserving already verified execution evidence and existing resources.

All setup choices, scope authorization and foreseeable human prerequisites are collected during intake. Use only actual user answers/consent; the agent can record their words but cannot approve for them. The current execution request and the completed confirmed scope must agree. A saved file grants no standing authority for unrelated resources or new actions. Credentials stay in protected stores; intake/state contain references only. No Client Discovery service, project UUID, export, app review or external workbook is required.

Operator profile

The intake's protected external operator reference identifies the existing operator. Resolve it as data, not commands. Keep the JSON file outside Git, owner-only (0600 in private directories). It contains references, never token, password or private-key values:

Live readiness gate

After intake passes, verify actual checkout and resource ownership, intended GitHub actor/admin/plan/Actions support, selected-repository App access, strict SSH host trust, reviewed operator source/configuration/current-boot receipt, DNS zone authority/conflicts, available ports/capacity, supported backup adapter, and local tools including an unattended path for both saved IDE launches. Use the existing operator interfaces; unreviewed host repair is a blocker.

Write a nonsecret resolved plan and results to .template-initialization/readiness.md. Readiness-only requests stop here. Runtime/IDE/browser, deployed CI and initialized recovery evidence are collected after personalization, not inferred from preflight checkboxes. Missing access or changed scope produces a precise blocker and an intake update where needed. Continue only matching authorized independent work. Mandatory tool/provider approvals remain in force.

Execution and resume

Keep ignored .template-initialization/state.json under owner-only permissions with atomic writes. Record version, exact repository/root, initial commit, intake revision/digest/scope, phase states, source/run/image/resource identities, protected credential references and redacted failures/recovery transaction IDs. Never execute values as commands. Reconcile actual state before retries and preserve volumes/passwords. Existing completed consumers retain their evidence; read-only reconciliation never recreates their setup. A missing new intake only blocks new execution, not the validity of historical acceptance.

Regenerate docs/project.html and the bundled offline view using the dashboard procedure. Report actual checks, missing evidence, deferred artwork and any human intervention after intake. Configuration alone does not prove runtime or live setup. A clean fresh-consumer rehearsal is still required to prove the unattended experience. Business requirements/specification are a later separately defined workflow.

Procedure

Initialize a project from this template

This is the authoritative application identity replacement map and setup-owner guide. The execution skill runs the approved phases; the contract owns readiness, scope, resume and acceptance. Complete the sibling intake skill first. Its private answers and confirmed scope replace external preparation workbooks.

Full setup includes local development, shared CI/main protection, DNS, private images, two paired deployments and verified recovery. Local-only scope remains local. Keep existing infrastructure and application owners; new foundation installation, privileged upgrades and data replacement are separate work.

Resolve approved operator/account references and recheck readiness against live resources. Intake completion does not prove post-personalization runtime acceptance. Keep execution reports in .template-initialization/.

2. Establish the data and resume boundary

Check whether the consumer already has an identity recorded in its README or configured in the application. If requested values already match, verify them instead of rewriting. For an incomplete initialization with that same identity, finish only the missing changes. A different existing consumer identity is a later rename: report the boundary and require separately authorized scope. Completed consumers retain their accepted setup; a missing new preparation file does not authorize reinitialization or invalidate existing acceptance.

Check for existing local environment files and Docker resources using names and labels, without printing environment values. Changing the Compose project name changes its generated volume/network names; it does not rename or migrate a database. New database/user settings also do not change an initialized PostgreSQL volume.

For a fresh clone, update the committed environment example before generating local credentials or starting PostgreSQL. If a local database or an existing environment file uses the old identity, report the mismatch and require a explicit user decision recorded in intake before changing identity or starting another database. Preserve existing passwords, volumes, and data. Data migration, volume deletion, and password resets are outside this runbook. Resolve known mismatches during preparation/readiness. A newly discovered mismatch during execution blocks the affected phase until safely reconciled within the approved scope; it is not permission to reset data.

Done when: initialization can proceed without replacing an existing identity or hiding an existing database behind newly generated resource names.

Inspect both repository-derived GHCR package names before authorizing writes. An existing package owned by another repository is a preserve/block boundary, not an implicit takeover. Preserve conflicting packages and stop; registry replacement is separate explicitly authorized work, not a normal initialization action. Preserve repositories, credentials and data.

Private state and helper API

Run Node 24 from the consumer root (use its local Node launcher when needed):

node .agents/skills/initialization-intake/scripts/intake.mjs init --root /absolute/consumer
node .agents/skills/initialization-intake/scripts/intake.mjs status --root /absolute/consumer
node .agents/skills/initialization-intake/scripts/intake.mjs save --root /absolute/consumer --input /private/patch.json
node .agents/skills/initialization-intake/scripts/intake.mjs complete --root /absolute/consumer --input /private/confirmation.json
node .agents/skills/initialization-intake/scripts/intake.mjs require-complete --root /absolute/consumer

--input - reads JSON from stdin, avoiding scratch files. File inputs must be user-owned regular 0600 files. The helper uses Node core and local Git only; status and execution gating create no files and make no API requests. A helper invoked from elsewhere still writes inside the selected consumer, never beside its source helper. Use matching installed helper bytes for that consumer.

init creates missing private state and preserves existing state. status returns completion, revision, missing/invalid IDs, proposed/answered IDs and blocked prerequisites, without printing answers/evidence. Missing fields are unanswered; proposed and unknown values remain incomplete. Inspect the private file to resume actual answers; never copy it to public artifacts.

save shallow-merges field entries, increments the revision and clears any completion. Every patch supplies the revision just read; a conflict requires reloading and merging rather than overwriting another session. Example:

{
  "expectedRevision": 0,
  "answers": {
    "display_name": { "status": "answered", "value": "Inventory" },
    "backup_timezone": { "status": "proposed", "value": "Europe/Zagreb" },
    "initial_email": { "status": "unknown" }
  },
  "prerequisites": {
    "app_consent": {
      "status": "blocked",
      "evidence": "Owner still needs to select this repository."
    }
  }
}

Answer statuses are answered, proposed, unknown. Preserve the user's value, including invalid answers, and clarify them; the gate rejects invalid required answers rather than silently normalizing them. Prerequisites are ready, blocked, unknown; ready requires nonempty nonsecret evidence. Unknown fields and top-level approved/complete flags are rejected. All IDs and value contracts come from the catalog.

After all required questions and prerequisites are satisfied, show the full resolved plan and action list. Supply the actual user response:

{
  "expectedRevision": 4,
  "confirmation": {
    "response": "Use those targets and proceed with the listed setup actions."
  }
}

complete validates the current answers and evidence, increments the revision, and records the response and timestamp with a SHA-256 binding to all inputs, repository/worktree, revision and installed helper/schema bytes. It cannot prove that a response came from a human; the agent must preserve the real chat response and its meaning. This is an accidental-drift gate, not a cryptographic signature or standing execution authority. The explicit execution request remains required.

require-complete succeeds only for valid completed state matching this exact consumer. It returns complete, statePath, revision, repository, scope and digest (plus progress IDs); execution reads answers from statePath and retains the digest with its own .template-initialization phase evidence. Missing, partial, malformed, edited, stale or mismatched state exits nonzero and explicitly directs the user to finish $initialization-intake before execution.

The ignored state/ directory is 0700; JSON/temp/lock files are 0600. Writes are atomic with an exclusive writer lock and revision check; symlinked state/helper paths and hard-linked state files are rejected. If a process crashes with a lock, inspect active writers and the unchanged JSON before removing only that stale lock. Never delete the JSON as a retry shortcut.

Changed helpers/schema make old completion stale. Inspect the saved answers against the current catalog and use save with the old revision to reconcile any answers/prerequisites, adopting the current schema and clearing completion; review and complete again. A changed repository/worktree requires explicit identity reconciliation: preserve the old file privately, verify actual origin, then initialize the new target and re-confirm applicable answers. Never silently rebind completed state or replace another project's intake.

This folder's .gitignore and the repository ignore protect normal publication. Before committing, verify state/intake.json is ignored and absent from staged files; never force-add it. Secret-pattern checks catch common mistakes but cannot determine whether arbitrary text is a credential: record references only.
