# Setup questionnaire

For a [dry run](dry-run.md), present this same questionnaire for a hypothetical
consumer and explicitly simulated prerequisites. Keep examples proposed until
the user accepts them; practice never requires actual service login or access.

The executable catalog in [schema.mjs](../scripts/schema.mjs) owns field IDs,
validation and required prerequisites. Read the full catalog before presenting
questions. Ask all applicable questions upfront, including actions the user must
perform outside chat. Group them as below; do not turn setup into a business
requirements interview. The supported stack, theme, 30-day retention and existing
operator procedures remain constraints, not invitations to redesign them.

| Group                      | Settle before execution                                                                                                                                                                                        |
| -------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Outcome and target         | `execution_scope` (`full` or explicitly `local-only`), exact detected `repository`, fresh/resume boundary and preserved resources.                                                                             |
| Identity                   | Slug, display name, Java application namespace, PWA short name, exact localization policy, retained artwork or supplied asset reference, retained theme.                                                       |
| Local development          | Port allocation, dependency-install bounds, current data ownership, available runtimes/Docker/browser tooling, IDE trust/extensions/import and private credential destination.                                 |
| Accounts                   | Initial username, display name and email; separate credentials are generated by execution into protected storage. A username such as `admin` adds no role.                                                     |
| GitHub and CI (full)       | Intended account, scoped login versus explicitly allowed global switch, maintainer allowlist, private repository/admin/Actions support, selected-repository consent for the existing App.                      |
| Existing operator (full)   | Protected profile reference with actual host identity, canonical reviewed CI source/receipt, host trust, capacity, project path namespace and allowed loopback port range. Reuse existing shared CI/App/host.  |
| DNS and registry (full)    | Distinct owned staging/production FQDNs, exact zone/project access through the profile, existing records versus missing-record creation, absent packages versus same-repository resume, real push/pull access. |
| Backup and recovery (full) | Supported destination reference or same-server, explicit host-loss acceptance for same-server, supported daily time/IANA zone, 30-day retention, unscheduled staging, isolated scratch restore target.         |
| Authority and bounds       | Zero new paid resources, all existing unrelated resources preserved, exact `action_scope`, actual user confirmation after the complete resolved summary.                                                       |

For each topic, include detected facts, proposed defaults, questions, foreseeable
human actions and the evidence needed. Resolve reusable-profile facts by reading
the selected protected profile and verifying access; a profile default cannot
accept the consumer's risk. Record exact selected targets and evidence without
credential contents. Unsupported provider adapters, replacing registry packages,
new foundations, host repairs/upgrades, different-identity renames, existing DB
replacement, password resets and live restores need separately scoped work.

The existing operator profile is an external protected JSON document, version 1,
with `name`, `github` (host/account/allowed owner), `ssh` (target, identity reference,
verified host key, privilege mode), `ci` (existing pool, canonical source/revision,
installed configuration and App metadata/key **paths**), `dns` (provider/zone/
project/credential reference), `deployment` (host/project namespace/ports/
maintainers), `backup` (supported adapter/schedule) and `bounds`. It contains
references rather than credential values. A missing profile is prepared by the
operator before execution; it is not permission to bootstrap another shared pool.

Readiness evidence records what was verified and where, distinguishing actual
read-only checks from user attestations. Recheck volatile access/ownership before
writes during execution; a later outage blocks the affected phase without
repeating already answered configuration questions.

For local-only scope, full-only questions/prerequisites are inapplicable; explain
that CI, hosting, deployment and recovery acceptance remain outside that scope.
Use only local actions. Full scope requires every full prerequisite and action;
partial answers cannot masquerade as a completed full initialization intake.
