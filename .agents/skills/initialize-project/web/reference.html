Consumer initialization contract

This is the preparation, authorization, resume and acceptance contract for initialize-project. The runbook owns exact edits and links to operator procedures. The preparation workbook owns human service steps and answers. The skill alone owns maturity and learning-edit policy.

Supported scope and target

Initialize one existing private GitHub repository created from the template. Preserve one Git worktree with backend/ and frontend/, the existing stack, session authentication, frontend examples, path-aware Hetzner CI and two paired manual deployments. Use an existing approved shared CI pool and deployment host. New foundation installation, shared privileged code changes, host rebuilds, database replacement and business-feature development are separate scopes.

Read Git/GitHub metadata instead of assuming the folder name, current CLI account, organization or template examples describe the consumer. Protect the canonical vireocodedev/web-app-starter remote from consumer initialization. Missing Git identity, a different existing application identity, unexpected local changes or existing data must be resolved in intake before mutations. Preserve data and credentials; a later project rename is not fresh setup.

Written preparation

Advisory project phase

A bare skill invocation first reports the intended production project's developer preparation, recorded consumer initialization and client scope using the status contract. This is metadata inspection, not live deployment acceptance or authorization to initialize, lock, export or generate specifications. The optional protected project association remembers the user-supplied ID; conflicting repository/project/API bindings are preserved for explicit reconciliation. Preparation and client approvals remain independent. An older locked export may remain available while a newer scope is unfinished.

Preparation for selected initialization

Before fresh initialization, the developer completes and explicitly reviews preparation in Client Discovery for the intended production project. The initializer automatically fetches that reviewed revision with the supplied projectId, using the protected user-local profile described in the preparation guide. The standalone helper verifies schema, project/revision/review metadata, exact workbook SHA-256 and the actual consumer Git remote. It stores /.template-initialization/preparation.md and its nonsecret preparation-provenance.json under a user-owned 0700 directory as regular 0600 files. Existing manual format-1 workbooks remain supported. Read the complete workbook; do not replace it with a configuration interview, old conversation or guessed defaults. Only supported use-profile answers delegate values to the explicitly selected protected operator profile.

The agent discovers facts it can verify, rather than asking the human to guess repository IDs, current permissions, record contents, resource ownership or free ports. Human identity, risk, data-boundary and resource-scope choices remain explicit written answers. Keep the stack and business-feature scope unchanged.

The initialization contract owns the ordered setup phases and their evidence. If a record is malformed or belongs to another repository, report the discrepancy rather than treating it as a passed gate.

Present an actionable report

Use a compact table with project/source, developer preparation, recorded setup, current scope, and latest locked export. Give one next action, together with any independent work that can already proceed. Prefer identity/access reconciliation first; for incomplete setup, preparation/review/renewal or the next setup phase; after setup, the current scope's approval/lock step and specification handoff. Interpret the returned state fields: a successfully printed report can contain unavailable or blocked states and is not itself a readiness pass.

For example, an observed initialized consumer with reviewed execution preparation and fully approved but unlocked scope should say:

Setup completion is recorded. Developer preparation is reviewed and valid. Scope version 2 has both approvals and awaits administrator locking. Lock that version, then generate its specification into your chosen folder.

After a bare invocation's report, offer initialize/resume, live readiness, specification generation, or refresh status, with free-text input. Wait before starting the selected task. A concrete status request ends with the report. The baseline lock proves neither a completed specification nor issue publication or application implementation; those require their own artifacts and instructions.

Rehearsal lessons

These are generic prevention rules from an earlier consumer rehearsal, not acceptance evidence for this template or another consumer. A clean fresh-consumer run is still required to prove the complete no-follow-up initialization experience.

Observed bottleneckRequired prevention
CLI identity differed from the repository ownerSelect the protected account/profile before invocation; verify access and prefer scoped authentication.
Existing application/database identity was ambiguousRecord fresh versus same-identity resume and preserve existing resources.
Identity, artwork, accounts and backup risk needed human decisionsCollect explicit workbook answers before bulk changes.
Operator/profile discovery happened lateArrange the existing operator reference and verify current source, trust, receipt and capacity upfront.
Selected-repository App access needed owner browser consentComplete the existing App's saved repository selection beforehand; repository administration alone is not proof.
Old image namespaces belonged to different repositoriesInspect package ownership, preserve by default and require exact deletion rows, version counts and digest-loss consent.
Approved package deletion lacked CLI scopeComplete GitHub's conditional native authorization before invocation.
Port defaults collided with another applicationVerify ownership and allocate only approved unused ports; update all dependent surfaces.
IDE import name differed from Gradle identityOmit the optional single-backend projectName; verify the actual saved launch after personalization.
Generic Java launch did not prove saved IDE launchesVerify an unattended tool path for both configurations during readiness, then test real launches.
Empty reviewer settings invoked unavailable private-plan featuresOmit unused protection fields and verify actual readback; do not upgrade plans implicitly.
A Python isolation flag hid an installed CLI's sibling modulesUse the operator-documented interpreter/entrypoint; verify --help and real backup behavior.
A transient container startup failed CIKeep the failing required check; diagnose/retry within scope without weakening isolation.

Human login/2FA, App consent, credential entry, identity/risk choices and written authority remain human tasks. Client Discovery collects preparation; only live verification can establish runtime, CI, deployment and initialized recovery acceptance. Unexpected post-intake assistance is a preparation defect to record, not a reason to claim a no-follow-up success.
